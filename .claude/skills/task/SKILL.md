# 작업 태그 처리 절차

작업의 기준 데이터는 `docs/tasks/tasks.json` 하나뿐이다. 아티팩트(사람이 편집하는 현황판)는 읽지도 쓰지도 않는다.
모든 명령은 저장소 루트에서 실행한다.

## 0. 요청 종류 판단
| 요청 | 갈 곳 |
|---|---|
| 태그 + 작업 지시 ("SV5 해줘", `/task SV5`) | 1. 작업 진행 |
| 태그 없이 "이어서 해줘" | 현재 브랜치 이름(`git branch --show-current`)에서 태그를 찾는다 → 1. 작업 진행. 브랜치에 태그가 없으면 `task.py status`의 doing 목록을 보여주고 어느 작업인지 묻는다 |
| "SV2 완료 처리", "FE3 다시 todo로" | 2. 상태만 변경 |
| "진행 상황", "뭐 하면 돼?", `/task status` | 3. 현황 |

## 1. 작업 진행

### 1-1. 확인
1. `python3 docs/tasks/task.py show <태그>`를 실행해 담당자, 작업 내용, 선행 작업 상태, 참조 문서, 수정 허용 경로를 본다.
   - 태그 접두사와 담당자는 다를 수 있다(예: CL1, SV8은 P5). 담당은 `show`의 "담당"을 따른다.
   - 지시한 사람이 담당자가 아닌 것이 드러나면(자기 이름이나 P번호를 말한 경우) 알려주고 계속할지 묻는다.
2. 상태가 이미 `done`이면 알려주고, 다시 할지 묻는다.
3. **선행 작업 중 미완료가 있으면** 바로 멈추지 않는다.
   - `git fetch -q`를 하고, `git log origin/main --oneline -20`과 `git branch -r | grep -i <선행 태그>`로 실제 진행 여부를 확인한다.
   - 사람에게 상황과 선택지를 준다.
     - 목 데이터나 임시 구현으로 먼저 진행한다. FE는 같은 타입의 목 훅을 쓰는 것이 규칙이다.
     - 선행 작업을 기다린다.
     - 선행 작업이 사실 끝난 것이면 완료로 처리한다(2번 절차).
4. `refs`에 적힌 절만 읽는다. 예를 들어 "아키텍처 §4-1"이면 `docs/아키텍처.md`에서 `## 4.` 아래 `### 4-1` 제목을 찾아 그 절만 읽는다. 기획서도 같은 방식이다. 문서 전체를 읽지 않는다.

### 1-2. 시작
5. 브랜치를 만든다: `git switch -c feat/<태그 접두사 소문자>-<태그>-<짧은 영문 요약>` (예: `feat/sv-SV5-join-post`, `feat/op-OP1-legal`).
   - 이미 그 브랜치에 있거나 같은 태그의 브랜치가 있으면 그 브랜치를 쓴다.
   - 시작 전에 `main`을 최신으로 받는다.
6. `python3 docs/tasks/task.py set <태그> doing`을 실행한다.
7. 계획을 짧게 보여주고 진행해도 되는지 묻는다. 계획에는 다음을 넣는다.
   - 세부 작업별로 무엇을 만들지
   - 어떤 파일을 만들거나 고칠지
   - 완료 기준을 어떻게 검증할지
   - 사람이 직접 해야 하는 일(콘솔 설정, 계정 생성, 실기기 테스트 등)

### 1-3. 구현
8. 수정은 `paths`(수정 허용 경로) 안에서만 한다. `docs/tasks/tasks.json`, `docs/timeline.md`, `docs/timeline.html`은 항상 수정해도 된다.
9. **범위 밖 수정이 필요하면 직접 고치지 않는다.**
   - 예: CL 작업 중에 RPC 변경이 필요한 경우.
   - 그 경로를 맡은 담당자(P1~P5, CLAUDE.md "역할 경계" 표)에게 보낼 GitHub 이슈 초안을 만든다. 제목은 `[<그쪽 태그>] 요약`, 본문에는 아키텍처 명세와 다른 점, 재현 방법, 필요한 변경을 쓴다.
   - `gh issue create`로 올릴지 묻는다.
   - 그동안 쓸 수 있는 임시 처리를 제안한다.
10. 구현은 `docs/아키텍처.md`를 기준으로 한다. 명세와 다르게 해야 하면 이유를 설명하고 사람의 승인을 받는다. 승인되면 아키텍처 문서도 같은 PR에서 고친다.
11. 비밀값(service_role 키, SMTP 비밀번호, .env)은 절대 커밋하지 않는다.

### 1-4. 검증과 완료
12. 작업의 `done`(완료 기준)을 실제로 검증한다. 테스트, 빌드, `supabase db reset`, pgTAP, 린트·타입체크 등 실행할 수 있는 것은 실행한다.
    - 사람만 확인할 수 있는 항목(실기기, 메일 수신 등)은 확인 방법을 알려주고 결과를 묻는다.
13. **완료 기준을 모두 통과했을 때만** `python3 docs/tasks/task.py set <태그> done`을 실행한다.
    - 일부만 통과하면 `doing`을 유지하고, 남은 항목을 정리해 알려준다.
14. 커밋하고 push한 뒤 PR을 만든다.
    - 커밋 메시지: `<태그>: <요약>` (예: `SV5: join_post 행 잠금과 6단계 검증`)
    - PR 제목: `[<태그>] <작업명>`
    - PR 본문: 세부 작업 체크리스트, 완료 기준 검증 결과, 사람이 확인할 항목, 후속 작업
15. 결과를 보고한다. 넣을 내용은 다음과 같다.
    - 한 일
    - 검증 결과
    - PR 링크
    - 사람이 남은 할 일
    - 이 작업을 기다리던 후속 작업 중 이제 시작할 수 있는 것

## 2. 상태만 변경
1. `python3 docs/tasks/task.py show <태그>`로 현재 상태를 확인한다.
2. 확인할 수 있는 것은 가볍게 검증한다. 예: DNS 레코드는 `dig`, 파일이나 마이그레이션은 존재 여부.
   - 검증에 실패해도 사람이 원하면 그대로 바꾸되, 무엇이 확인되지 않았는지 말한다.
3. `python3 docs/tasks/task.py set <태그> <상태>`를 실행한다.
4. 현재 브랜치가 작업 브랜치가 아니면 `chore/status-<태그>` 브랜치에서 커밋하고 PR을 만든다. 팀이 main 직접 push를 허용하면 main에 커밋해도 된다.
5. 이 변경으로 시작할 수 있게 된 후속 작업을 알려준다.

## 3. 현황
1. `git fetch -q`를 한다. 가능하면 `git show origin/main:docs/tasks/tasks.json`의 상태를 기준으로 보고, 로컬 브랜치에서 바뀐 상태가 있으면 그것도 따로 알려준다.
2. `python3 docs/tasks/task.py status`를 실행하고 요약한다. 넣을 내용은 다음과 같다.
   - 완료 수
   - 진행 중인 작업
   - 지금 시작할 수 있는 작업. 묻는 사람이 누군지 드러나면 `task.py status --owner <P번호 또는 이름>`으로 그 사람 작업을 먼저 보여준다.
   - 막힌 작업
   - 핵심 경로(`tasks.json` notes의 "핵심 경로")에서 늦어지는 것

## 충돌 처리
- `docs/timeline.md`나 `docs/timeline.html`에서 머지 충돌이 나면 직접 풀지 않는다. 충돌 표시를 지우고 `python3 docs/tasks/task.py gen`으로 다시 생성한다.
- `docs/tasks/tasks.json`에서 충돌이 나면 각 작업의 `status` 줄을 양쪽 중 더 진행된 값으로 고른다. 진행 순서는 todo < doing < done이다. 그다음 `gen`을 실행한다.
