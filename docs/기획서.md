# 배달음식 공동구매 매칭 앱 — 최종 계획 (전문 에이전트 검토 반영)

> 구현 기준이 되는 상세 설계(스키마, RPC, RLS, 알림, 환경)는 [아키텍처.md](./아키텍처.md)를 본다.

## Context
배달비와 최소주문금액 부담을 줄이려고 같이 주문할 사람을 찾는 수요가 있다. 이 앱은 **사람을 모으는 것**(글 작성 → 참여 → 채팅)에만 집중한다. 주문은 방장이 하고, 결제는 외부 PG 없이 **참여자가 방장 계좌로 직접 선송금**한다(수동 송금 방식, 2026-11-17 확정). 앱은 돈을 보관하거나 중개하지 않고, 방장 계좌를 참여자에게 보여 주고 송금 여부를 기록하는 데까지만 한다.
목표는 **App Store와 Play Store에 실제로 출시해서 운영하는 것**이다. 프로젝트 폴더(`배달음식/`)에는 아직 코드가 없다.
이 계획은 PM, Backend Architect, Mobile App Builder 에이전트의 검토를 반영했다.

**포지셔닝:** 같이 시킬 사람을 이미 알 때 쓰는 배민 '함께주문'과 경쟁하지 않는다. 이 앱은 **모르는 사람을 10분 안에 찾아 주는 것**에 집중하고, 함께주문 링크를 붙여 쓰는 보완재로 자리 잡는다.
**서비스 대상:** **POSTECH 구성원 전용**이다. `@postech.ac.kr` 메일 인증을 통과해야만 가입할 수 있다. 지역(zone)은 캠퍼스 안의 생활 구역(생활관 동, 대학원 아파트 등)으로 나눈다. 실제 구역 목록은 출시 전에 확정한다.

## 1. 확정 기능

### MUST (출시 필수)
- **가입과 로그인:** POSTECH 메일과 비밀번호를 쓴다. 자세한 내용은 "1-1. 인증 설계"를 본다.
  - 가입한 뒤 닉네임을 정하고, 캠퍼스 안 생활 구역을 직접 고른다. GPS는 쓰지 않는다.
  - 송금 받을 계좌(은행·계좌번호·예금주) 또는 토스 송금 링크를 등록할 수 있다. 가입 때는 건너뛸 수 있지만, **방장이 되려면(글 작성) 필수**다.
  - 첫 실행 때 접근권한 안내 화면을 보여준다.
- **피드**
  - 내 지역의 모집 중인 글을 마감 임박 순으로 보여준다.
  - 글이 없을 때는 "지금 글 올리기"와 "카테고리 알림 받기"를 띄운다.
  - 카테고리 필터는 빼고, 글마다 카테고리 태그만 표시한다.
- **글 작성**
  - 입력 항목: 가게명, 배달앱 또는 함께주문 링크(선택), 카테고리, 픽업 장소, 정원, 마감 시각, 배달비·최소주문 메모
  - 픽업 장소는 공용 공간 프리셋에서 고른다.
  - 마감은 15분, 30분, 60분 프리셋에서 고른다.
  - 첫 글 작성 전에 EULA(무관용 정책) 동의를 받는다.
- **참여**
  - 참여하면 바로 그룹 채팅방에 들어간다. 정원이 차면 참여 버튼이 꺼진다.
  - 방장과 서로 차단한 사이이거나 이용 제재 중인 사람은 참여할 수 없다.
- **상태:** 모집중 → 마감 → 완료 또는 취소. 마감 시각이 지나면 자동으로 마감하고, 마감 10분 전에 알림을 보낸다.
- **나가기 규칙**
  - 마감 전에는 자유롭게 나갈 수 있다.
  - 마감 후에 나가면 '이탈'로 기록하고 방장에게 알린다.
  - 방장이 나가면 다른 참여자에게 방장을 넘긴다. 받을 사람이 없으면 글을 자동 취소하고 전원에게 알린다.
- **송금(수동 선송금)**
  - 모집이 마감되면 참여자에게만 방장 계좌가 보이고 "송금해 주세요" 알림이 간다. 마감 전에는 계좌가 보이지 않는다.
  - 송금 기한은 마감 후 30분이다. 기한 10분 전에 아직 안 보낸 참여자에게 알림을 보낸다.
  - 참여자가 "보냈어요"를 누르고 방장이 "입금 확인"을 누른다.
  - 방장은 확인 전에 "입금 안 됨"으로 참여자의 "보냈어요"를 되돌릴 수 있다. 확인한 뒤에는 되돌릴 수 없다.
  - 기한이 지나도 "보냈어요"를 누르지 않은 참여자는 방에서 자동으로 빠진다(이탈로 기록).
  - 방장의 "주문하러 가기" 버튼은 남은 참여자 전원의 입금을 확인해야 켜진다.
  - 송금한 뒤 모집이 취소되면 방장과 송금한 참여자에게 환불 안내 알림을 보낸다. 환불은 사용자끼리 직접 한다.
  - 앱은 돈을 보관하지 않고 송금 여부만 기록한다. 이 기록이 분쟁 증빙이 된다.
- **노쇼·미송금 신고:** 3회 쌓이면 이용을 제한한다.
- **채팅**
  - 실시간 그룹 채팅, 시스템 메시지, 안 읽은 메시지 수
  - 상단에 "송금은 방장 계좌로 직접 해요. 앱은 돈을 보관하지 않아요" 안내를 고정한다.
- **카카오톡 공유와 딥링크:** 앱이 없는 사람이 링크를 누르면 웹페이지나 스토어로 보낸다.
- **푸시**
  - 보내는 경우: 새 참여자, 마감 임박, 상태 변경, 메시지(방별로 끌 수 있음), 관심 카테고리에 새 글
  - 송금 관련: 송금 요청(마감), 송금 기한 임박, 입금 안 됨, 입금 확인, 기한 초과로 빠짐, 환불 안내
  - 받는 사람이 지금 보고 있는 방의 알림은 보내지 않는다.
- **안전과 심사 대응**
  - 글, 메시지, 사용자 단위로 신고와 차단
  - 금칙어 필터와 도배 방지(글 작성·메시지 전송 횟수 제한)
  - 앱 안에서 계정 삭제(Play용 웹 삭제 URL도 준비), 이용약관과 개인정보처리방침
- **최소 관리자 도구**
  - 신고가 들어오면 Slack으로 알림을 받는다.
  - SQL 뷰와 RPC로 사용자를 정지한다.
  - 24시간 안에 처리하는 운영 체계를 둔다.

## 1-1. 인증 설계 (POSTECH 메일 전용)

### 원칙
- `@postech.ac.kr`로 끝나는 메일만 가입할 수 있다. 판정은 **서버에서** 강제한다. 앱에서 막는 것은 사용 편의를 위한 보조 장치일 뿐이다.
- 메일 인증을 통과해야 계정이 활성화된다. 인증하지 않은 계정은 어떤 데이터도 읽거나 쓸 수 없다.
- 인증 수단은 메일 + 비밀번호다. 휴대폰 SMS 인증은 쓰지 않는다. SMS 업체와 발송 비용이 필요 없다.

### 화면 흐름
1. **회원가입**
   1. 메일과 비밀번호를 입력한다.
   2. 약관, 개인정보처리방침, EULA에 동의한다.
   3. 인증 코드 6자리가 메일로 발송된다.
   4. 앱에서 코드를 입력하면 인증이 끝난다.
   5. 닉네임과 생활 구역을 설정한다.
2. **로그인:** 메일과 비밀번호를 입력한다. 아직 인증하지 않은 계정이면 인증 코드 입력 화면으로 보내고, "코드 재전송" 버튼을 준다.
3. **비밀번호 재설정:** 메일을 입력하면 재설정 코드 6자리가 발송된다. 코드를 입력하면 새 비밀번호를 설정한다.
4. **비밀번호 변경(설정 화면):** 현재 비밀번호를 다시 입력한 뒤 새 비밀번호로 바꾼다.
5. **로그아웃과 계정 삭제:** 설정 화면에서 한다. 계정 삭제 전에는 비밀번호를 다시 확인한다.

### 메일 판정 규칙
- 메일 주소에서 앞뒤 공백을 지우고 소문자로 바꾼 뒤 정규식 `^[a-z0-9._%+-]+@postech\.ac\.kr$`로 검사한다.
- 다음 형태는 거부한다.
  - 하위 도메인: `a@mail.postech.ac.kr`
  - 접미사 위장: `a@postech.ac.kr.evil.com`
  - 대문자, 공백, 특수문자를 섞어 우회하려는 입력
- 이메일 변경은 MVP에서 막는다. 나중에 허용하더라도 새 주소 역시 POSTECH 메일이어야 하고 다시 인증을 거친다.

### 서버 쪽 구현 (Supabase Auth)
- **도메인 강제:** Supabase의 **Before User Created Auth Hook**(Postgres 함수)으로 도메인이 맞지 않는 가입을 거부한다.
  - 거부 시 반환하는 에러 메시지: "POSTECH 메일(@postech.ac.kr)만 가입할 수 있습니다"
  - 이 hook은 API로 직접 가입하는 우회 경로까지 막는다.
- **이중 방어(RLS):** 모든 정책이 `is_verified_member()` 함수를 거치게 한다. 이 함수는 JWT의 `email`이 POSTECH 메일이고 `email_confirmed_at`이 있을 때만 true다. 그래서 hook 설정이 빠지는 사고가 나도 데이터는 노출되지 않는다.
- **인증 방식:** 링크 클릭 대신 **6자리 OTP 코드**를 쓴다. 메일 템플릿에 `{{ .Token }}`을 넣고, 앱은 `verifyOtp({ type: 'signup' | 'recovery' })`로 확인한다.
  - 링크 방식을 쓰지 않는 이유는 두 가지다. 학교 메일 보안 필터가 링크를 미리 열어 토큰을 소진시킬 수 있다. 또 모바일 딥링크 문제를 피할 수 있다.
- **메일 발송(커스텀 SMTP 필수):** Supabase 기본 SMTP는 시간당 발송량이 매우 적어서 운영에 쓸 수 없다.
  - 외부 발송 서비스는 **Resend**로 확정했다. 발신 도메인은 새로 구매한다(임시로 `example.kr`).
  - 우리 도메인에 SPF, DKIM, DMARC를 설정한다.
  - **POSTECH 메일 서버의 스팸 차단 여부를 1주차에 실제 계정으로 테스트한다.** 가장 큰 출시 리스크다.
- **비밀번호 정책**
  - 최소 8자, 영문과 숫자를 모두 포함한다.
  - Supabase의 유출 비밀번호 차단(HaveIBeenPwned) 기능을 켠다. Pro 플랜 기능이다.
  - 비밀번호는 Supabase가 bcrypt로 저장한다. 우리는 직접 저장하지 않는다.
- **요청 횟수 제한:** 인증 메일 재전송은 60초 쿨다운을 두고, 같은 메일에 시간당 최대 5회까지만 보낸다. 로그인 실패가 반복되면 Supabase 기본 rate limit이 막는다. 가입 화면에는 CAPTCHA(Turnstile)를 단다.
- **세션:** 액세스 토큰은 1시간마다 갱신하고, 리프레시 토큰은 MMKV에 저장한다. 앱이 다시 활성화될 때 `startAutoRefresh`를 호출한다.

### 운영과 정책
- **1인 1계정:** 메일 하나에 계정 하나다. 노쇼 제재도 메일 기준으로 건다.
- **탈퇴 후 재가입:** 메일 해시를 정해진 기간(예: 90일) 보관해서 제재를 피하려는 재가입을 막는다. 이 사실은 개인정보처리방침에 적는다.
- **졸업생과 퇴직자:** 학교 메일을 계속 쓸 수 있는 경우가 있다. **SHOULD**로 연 1회 메일 재인증을 둔다. 재인증하지 않으면 읽기 전용으로 바꾼다.
- **메일 비공개:** 다른 사용자에게는 닉네임만 보인다. `profiles` 테이블에 메일을 두지 않고, 메일은 `auth.users`에만 있다.
- **계좌 비공개:** 계좌는 별도 테이블(`payout_accounts`)에 두고, 그 사람이 방장인 방의 참여자에게 마감 뒤에만 보인다. 수집 항목과 보관 기간(탈퇴 즉시 삭제)을 개인정보처리방침에 적는다.
- **호실:** 제안서에는 수집 항목으로 올라와 있지만 쓰임이 정해지지 않았다. 쓰임이 정해지기 전에는 수집하지 않는다(결정 필요).
- **앱스토어 심사:** 심사관은 POSTECH 메일을 받을 수 없다. 팀이 미리 인증해 둔 심사용 계정(아이디와 비밀번호)을 심사 노트에 적어 준다.
- **기존 계획에서 빠지는 것**
  - 휴대폰 OTP와 SMS Hook(솔라피·NHN)
  - 학교 메일 배지(이제 전원이 인증된 사용자다)
  - 카카오 로그인과 Apple 로그인 계획(이메일 로그인만 쓰므로 Apple 가이드라인 4.8 대상이 아니다)
  - 만 14세 미만 차단 절차(약관 동의 체크박스로만 확인한다)

## 2. 확정 기술 스택
| 영역 | 선택 |
|---|---|
| 앱 | Expo SDK 최신(New Architecture), **dev client**(Expo Go 사용 안 함), Expo Router |
| 상태 관리 | TanStack Query(MMKV에 저장), Zustand |
| UI | NativeWind v4, @gorhom/bottom-sheet, 직접 만드는 공용 UI 컴포넌트 |
| 폼 | react-hook-form + zod(검증 스키마는 Edge Function과 공유) |
| 채팅 UI | FlashList v2 기반으로 직접 구현, react-native-keyboard-controller |
| 기타 클라이언트 | expo-image 계열, dayjs(ko), expo-notifications, @react-native-kakao/share |
| 백엔드 | **Supabase Pro, 서울 리전** |
| 인증 | Supabase Auth **메일 + 비밀번호**, `@postech.ac.kr` 전용(Before User Created Hook과 RLS로 이중 방어), 6자리 메일 OTP 인증과 비밀번호 재설정, 커스텀 SMTP(Resend), 유출 비밀번호 차단, Turnstile, 요청 수 제한 |

| 쓰기 경로 | **RPC로만 쓴다**: join_post, leave_post, change_status, send_message, mark_paid, confirm_paid, reject_paid, set_payout_account. 횟수 제한을 함께 건다. |
| 스케줄 작업 | pg_cron: 자동 마감, 마감 임박 알림, 송금 기한 임박 알림, 송금 기한 초과 처리, 90일 지난 메시지 삭제 |
| 푸시 발송 | 트리거 → **pgmq 큐** → Edge Function이 묶어서 Expo Push로 보낸다(같은 방 알림은 30초 단위로 합치고, 발송 결과 receipt를 처리한다). |
| 모니터링 | Sentry(앱과 Edge Function), PostHog |
| 배포·운영 | EAS Build/Submit/Update(fingerprint), GitHub Actions + `supabase db push`, pgTAP RLS 테스트, 주 1회 pg_dump 외부 보관 |

## 3. 데이터 모델 요점
- **posts**
  - 정원 확인용 `member_count` 컬럼을 둔다.
  - 부분 인덱스 `(zone_id, deadline_at) WHERE status='open'`를 건다.
  - 직접 UPDATE는 REVOKE하고 상태 변경 RPC로만 바꾼다.
- **posts**의 `pay_due_at`: 마감할 때 마감 시각 + 30분으로 채운다.
- **participants**
  - 컬럼: role, state(참여 / 나감 / 이탈 / 강퇴), paid_state(none / sent / confirmed), last_read_message_id, muted_until
  - `(user_id)` 인덱스를 건다.
- **messages**
  - 컬럼: bigint id, type, sender_id(null 허용), client_msg_id
  - UNIQUE `(sender_id, client_msg_id)`로 중복 전송을 막고, `(post_id, id DESC)`로 커서 페이지네이션을 한다.
- **payout_accounts:** 사용자당 1행. 은행·계좌번호·예금주 또는 토스 송금 링크. 본인과, 그 사람이 방장인 마감된 방의 참여자만 읽을 수 있다.
- **기타 테이블:** zones, profiles(deleted_at, 정지 여부), reports, blocks, push_tokens(한 사용자가 여러 기기를 쓸 수 있음), category_subscriptions
- **join_post 처리 순서:** 글 행을 `FOR UPDATE`로 잠근다 → 마감 시각 재확인 → 정원 확인 → 차단·제재 확인 → `ON CONFLICT`로 중복 참여 무시. 함수는 `SECURITY DEFINER`와 `search_path=''`로 만든다.
- **RLS:** `(select auth.uid())` 형태로 쓰고, `is_participant()`를 STABLE 함수로 만든다.
- **계정 삭제:** 프로필을 익명화하고 `auth.users`를 삭제한다. messages의 FK는 SET NULL이다. 재가입 악용을 막기 위해 전화번호 해시는 일정 기간 보관한다.

## 7. 검증
- **인증(pgTAP와 API 직접 호출):**
  - `a@gmail.com`, `a@mail.postech.ac.kr`, `a@postech.ac.kr.evil.com`, ` A@POSTECH.AC.KR `(공백) 중 정규화 후 올바른 메일이 되는 마지막 경우만 가입되고 나머지는 거부되는지 확인한다.
  - 인증하지 않은 계정의 토큰으로 posts와 messages를 조회하면 0건인지 확인한다.
  - 인증 코드가 만료되면 실패하는지, 재전송 쿨다운이 동작하는지 확인한다.
- **메일 도달:** 실제 POSTECH 메일함으로 가입 메일과 비밀번호 재설정 메일이 받은편지함에 1분 안에 오는지 확인한다(스팸함 여부도 확인).
- **RLS(pgTAP):** 다른 지역의 글과 참여하지 않은 방의 Broadcast 채널에 접근할 수 없는지 확인한다.
- **동시성:** 정원이 1명 남은 글에 동시에 2명이 참여하면 1명만 성공하는지 확인한다.
- **마감:** 마감 시각이 지난 글에는 cron이 돌기 전이라도 참여할 수 없는지 확인한다.
- **송금:** 마감 전에는 참여자도 방장 계좌를 볼 수 없고, 비참여자는 마감 뒤에도 볼 수 없는지(pgTAP). 기한이 지나면 안 보낸 참여자가 빠지는지, 미입금자가 있을 때 "주문하러 가기"가 잠기는지 확인한다.
- **전체 흐름:** 실기기 2대로 글 작성 → 참여 → 채팅 → 마감 → 송금·입금 확인 → 완료를 진행하고, 백그라운드에서 돌아왔을 때 빠진 메시지가 복구되는지, 푸시가 어떻게 묶여 오는지 본다.
- **스토어 체크리스트:** 신고, 차단, EULA, 계정 삭제, 권한 안내, 카카오 공유가 운영 빌드에서 동작하는지 확인한다.
